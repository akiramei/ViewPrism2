## 4. 言えること / 言えないこと

**言えること(手順)**: 履歴のない許可ファイル集合・3 役の分離・裁定の事前封印・訂正の追記履歴・パッケージ外アクセスの監査は、
Codex の独立セッションで運用として回った。所要は改善 13 分・裁定 4 分・予測 4 run 各 5〜10 分。

**言えること(事例)**: この事例では BOM A だけで実 diff の src 変更 unit(M-DB-007)に 4/4 で到達した。根拠は BOM に残る
類似事例(ECO-098)の記録であり、E/M の依存関係や契約からの導出ではない — **これは正当な BOM の利用**である(依存グラフだけが
BOM の価値ではない。事例知識と構造情報の併用が製品開発上は有用)。「BOM が活躍していない」という事前の見立てはこの結果で更新する。
tests unit は BOM 経路で辿られなかった(原因未確定)。今回生成された B では主評価の集合に改善が観測されなかった(測定範囲内の結論)。
**中心的な発見(訂正後)**: BOM は事例知識として既に使われ、M unit レベルの契約には ECO-140 の実装写像も既に取り込まれていた。
改善工程が生成しなかったのは **E 品目レベルの依存辺**(E-UI-INTEGRITY-050 → E-DB-010)であり、「改善指示から狙った BOM 改善が
生成されるか」という上流の課題は残る。ただし「実装との対応を取り込む工程が機能していない」とまでは言えない(M-DB-007 契約は ECO-140 の
クローズ時に更新されていた)。製造者の読み違い(A の写像有無)は EXP-20260905-04 の参照表(独立作成)が捕捉した — 封印 oracle の誤りを
多腕/独立作成が検出する 2 例目(ET-002 に続く)。

**言えないこと**: BOM 改善が変更予測を改善するか(N=1・改善内容が事例の要所に触れていない)/ A と B のコスト差の再現性 /
到達モデル・到達 effort / 裁定者の行動上の盲検(構造でのみ担保)。

## 5. 次の優先順位(レビュー 2026-09-05 を反映)

1. **結論を測定範囲に合わせ、トークン差の内訳を確認する** — 本版で実施(§2・§4)。
2. **改善者が、対象を名指しされずに実装との対応漏れを発見・補完できるか**を確認する。今回の改善工程は order の設計変更を反映したが、
   diff が生んだ実装写像(件数クエリ→M-DB-007)を落とした。改善者の入力に「diff から実装写像を抽出し `(observed@rev)` で記録する」工程を
   明示した条件と、今回の条件を比較する(改善指示の設計そのものが対象)。
3. **テスト unit を含む予測様式を固定する**(製品 unit と検査 unit を分ける)。入力条件の変更なので、旧条件との比較で様式の効果を
   BOM 改善の効果に混ぜない。
4. **その条件で前向きの変更を観測する**(ECO-082 の着手、または次の実変更)。履歴記述の有無の比較は、依存導出の寄与を調べる副実験に
   留め、通常運用から履歴記述を除く方向には進めない。
5. 裁定の訂正語彙: 「是正方針の選択で不要化」は使えるが、当初の必須判定が過大だった場合は**裁定の訂正**として明示する(§2・履歴 訂正 1)。
